# Performance Budgets

Budgets come from PRD §33 plus additions we own. They are **product targets, not hard guarantees
for every repository** (PRD §33 says exactly that) — but a claim that we meet one is only valid
with a measurement behind it. Owning agent: `performance-scalability`; skill:
`performance-investigation`; review command: `/review-performance`; new-budget proposals use
`.claude/templates/performance-budget.md`. Related: `testing-strategy.md` §1.10,
`architecture.md` (worker-process indexing), ADR-0006 (persistence sizing).

## 1. Budget table

| #   | Budget                                                   | Target                                                                                   | Source                              |
| --- | -------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ----------------------------------- |
| B1  | Extension activation (no indexing in the extension host) | < 500 ms                                                                                 | PRD §33                             |
| B2  | Initial index, 5,000 source files, typical dev machine   | < 2 min                                                                                  | PRD §33                             |
| B3  | Incremental update after a small change                  | < 3 s (where practical)                                                                  | PRD §33                             |
| B4  | Impact-tree first results, pre-indexed repository        | < 15 s                                                                                   | PRD §33                             |
| B5  | Graph view default visible nodes                         | < 200                                                                                    | PRD §33                             |
| B6  | UI responsive during indexing (no frozen webview/tree)   | always                                                                                   | PRD §33                             |
| B7  | Cancellation acknowledged (any long-running use case)    | < 500 ms                                                                                 | ours (SKILL.md §7)                  |
| B8  | Single JSON artifact size                                | ≤ 5 MB target                                                                            | ours (ADR-0006)                     |
| B9  | Per-workspace artifact store                             | ≤ ~25 MB before SQLite migration is triggered                                            | ADR-0006 revisit threshold          |
| B10 | AI context budget per request (`selected-snippets`)      | declared per request; evidence ranked + deterministically truncated, truncation recorded | ours (`ai-provider-boundary.md` §4) |

B1 and B6 are structural: indexing runs in a worker/child process, **never** the extension host
(PRD §33) — no budget tuning compensates for violating that.

## 2. Benchmark fixtures

Benchmark fixtures live in `packages/test-kit/fixtures` beside the analyzer fixtures
(`testing-strategy.md` §2); large ones may be generated by a test-kit script rather than committed
file-by-file, but generation must be deterministic (seeded).

| Fixture       | Shape                                               | Exercises                                 |
| ------------- | --------------------------------------------------- | ----------------------------------------- |
| `small`       | ~50 files, single app                               | B1, B3, B4 floor; regression canary       |
| `medium`      | ~1,000 files, one framework (e.g. NestJS)           | B2 scaling curve, B4                      |
| `large`       | ~5,000 files                                        | B2 (the headline target), B3, B7          |
| `monorepo`    | multi-app workspace (several packages/services)     | context grouping, B5, cross-app traversal |
| `large-diff`  | fixture + generated diff touching hundreds of files | review pipeline, B7                       |
| `large-graph` | dense dependency web (>200 candidate nodes)         | B5, progressive disclosure, layout time   |

## 3. Measurement methodology

- **Measured, not intuited.** No PR may claim a performance improvement or budget compliance
  without numbers. `/review-performance` is the workflow; it records the numbers in the PR.
- Repeatable runs: fixed fixture + seeded generation, ≥ 5 runs, report median and worst; cold vs
  warm (index cache present/absent) reported separately.
- Record the environment (machine class, Node 22 version) with every baseline.
- Baselines are **recorded and committed** with the benchmark results notes accompanying the
  change that established them; a regression is a diff against the recorded baseline, not against
  memory.
- Instrument via the analysis-run record itself where possible (index duration, phase timings are
  product data — PRD §36 allows duration buckets in opt-in telemetry).
- Benchmarks run locally on demand and mandatorily before release
  (`.claude/templates/release-checklist.md`); they are not a per-PR CI gate — CI runners are too
  noisy for millisecond budgets, and a flaky gate would erode the no-weakening rule
  (`quality-gates.md`).

## 4. Large-monorepo fallback behavior

When a repository blows past the `large` fixture scale, the product degrades progressively rather
than missing budgets silently (PRD §33 progressive disclosure, §43.1 graph explosion):

- Context-level default view; symbols expanded on demand only.
- Node limits + filters keep the graph under B5; the impact **tree** is the primary interface and
  must stay usable when the graph is capped (PRD §37: the graph is never the only access path).
- Indexing reports progress and remains cancellable within B7; partial indexes are persisted
  safely; a failed index never destroys the previous valid one (PRD §34).
- Analysis continues with partial language support, reporting unsupported files clearly (PRD §34).
- If B2/B3 cannot be met, the UI says so (estimated time, scope options) instead of hanging.

## 5. Honest caveat

PRD §33: "These are product targets, not hard guarantees for every repository." We treat a missed
budget as a bug to triage with data, not a promise broken — and we never delete a budget to make
the miss disappear. Changing a budget value requires the `performance-budget.md` template, a
recorded measurement justifying it, and human approval.
